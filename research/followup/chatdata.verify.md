# Verification: follow-up track "chatdata" (chatdata.md)

Adversarial fact-check of `research/followup/chatdata.md`, 2026-09-23. Each load-bearing claim was checked against a primary source: model cards and `config.json` pulled raw from Hugging Face, the HF datasets-server and API, arXiv abstract, HTML and PDF text, GitHub issue bodies via the GitHub API, the TII blog, and Apple's newsroom. Verdicts: confirmed, corrected (gist holds, a number, scale or attribution is off), refuted, unverifiable. No model was loaded or run.

**Limits of this check.** The session's WebSearch budget was already used up when this check started, and the arXiv search endpoints returned HTTP 429. The omission and novelty searches therefore used direct fetches of known papers, the Hugging Face Hub dataset search API, the Hugging Face papers index, and the GitHub issue search API. Absence claims (no dataset exists, no one has tried X) are weaker than usual here, and I never mark one "confirmed".

## Short version

- **The teacher and model facts are right.** Gemma 4 26B-A4B's license (Apache 2.0), architecture (30 layers, 25 sliding + 5 global, 128 experts top-8 at width 704 plus a 2112-wide shared FFN, vocab 262,144), thinking switch, empty thought block, thinking-mode-only IF scores and Arena Elo all match the card, `config.json` and the Gemma 4 report. The MoE batching arithmetic reproduces exactly.
- **Four corrections matter for planning:**
  1. **Metal limit.** On a 24 GB Mac the default GPU working set is about **2/3 of RAM (16 GiB)**, not 75%. A Mac mini M2 with 24 GB logs `recommendedMaxWorkingSetSize = 16384.02 MB` ([llama.cpp #3911](https://github.com/ggml-org/llama.cpp/issues/3911)). The report's 16-18 GB range covers the value, but Gemma 4 26B-A4B's measured 17.1 GB at 4k context sits at or above 16 GiB. So the 26B-A4B verdict ("poor fit") is if anything too gentle.
  2. **Generation throughput is unanchored and probably optimistic.** The only measured batched MLX number scales to roughly **45-70 raw tok/s** for an 8-12B dense 4-bit teacher on the base M5 (derived below). That is below the report's 100-300 *accepted* tok/s even before yield losses. On that anchor, 100M accepted tokens is roughly 20-50 Mac-days, not 4-12. The Mac training rate the report uses (10.6-11.8k tok/s at 18.5M) is marked **unverifiable** in `lanes/compute.verify.md`: a re-run under contention got about half.
  3. **Falcon-H1-Tiny also tested 75% and 100% SFT shares, and both were "suboptimal overall".** That is direct prior evidence against ledger idea L7's hypothesis, and the report leaves it out.
  4. **The paper behind the "statistically narrow" design rule also reports brittleness.** Readability ≠ Learnability (262K-33M params) finds that models trained on narrow synthetic data see coherence "degrade substantially" on prompts from any other distribution, including web text. That bears directly on Planck's real-conversation test, and the report omits it.
- **Ledger novelty is overstated for L7, L8, L9, L10 and L11, and partly for L1.** Each has a published precedent: the TII ratio sweep; prompt-loss masking studies; LongCE and token weighting; phrase-based refusal filtering; Physics of LMs 2.2 at about 100M, which found that errors followed by corrections help and that masking the errors is unnecessary; and DST training on MultiWOZ with GPT-2. None of these precedents tests the exact tiny-scale chat-memory version. The ideas are still worth running, but they should cite the prior results and include the arms those results suggest.
- **Biggest omission:** the 2026 micro-LM paper (arXiv 2604.19642). It pretrained 8.8-29.5M models from scratch on 100% multi-turn chat data (1.485B tokens, 12,288-token BPE vocab), and they were competitive with 70M-256M models on short dialogue responses. This is the closest published work to Planck's size and data regime.

## 3. Scale misapplications

1. **Readability ≠ Learnability (stories, 262K-33M) is used as the design rule for multi-turn chat skills, and only its favourable half is carried over.** The scale fits Planck, but the domain differs (single-author stories, no cross-turn dependency). The same paper reports that narrow-distribution models are brittle out of distribution, which is the risk for a real-user test.
2. **TinyStories' depth-over-width result for instruction following** (single-prompt story constraints, 1M-80M) is extended to "cross-turn recall is an instruction-following-like global-attention skill". The scale is right, but the skill transfer is an inference.
3. **Pleias-RAG-350M/1B** (vendor; the claim covers the 350M and 1B jointly) is the evidence that the lookup variant can be learned at 20-60M (section 3.5, L15). That is a 6-17x downward extrapolation.
4. **Falcon-H1-Tiny 25% SFT share** (90M, 100-800GT, knowledge-bearing Tulu 3 mix, IFEval metric) sets the chat share and the unique-token target for a 10-20M knowledge-free model. The report flags the metric mismatch but not that TII's own 75-100% arms failed.
5. **vllm-mlx batching gains on an M4 Max** (546 GB/s, 40 GPU cores) inform the runtime choice for a base M5 (153 GB/s, 10 cores). This is a hardware-scale transfer, and the report's 100-300 accepted tok/s goes well beyond what that anchor supports.
6. **Longpre et al. entity substitution** (QA reader models, sizes not checked by the report) supports nonce slot values (L5) at 20M. The report hedges this, but it is still larger-model, different-task evidence.
7. **Multi-turn data results** from Parrot (13B), ConsistentChat (7-8B), TurnWise (Olmo 3 7B) and SmolTalk2 (3B) are correctly flagged [>=1B only] in the table. The bottom line's framing that "multi-turn-skill synthesis exists" should not be read as evidence that such data moves skills at 10-150M. At about 151M, the only in-range datapoint (ufakzeka-1) is null.

## 4. Novelty overclaims (ideas marked untested that have precedents)

- **L7 (chat share above 25% at 10-20M).** TII already swept 0/25/50/75/100% SFT data at 90M in 100GT runs. 25% and 50% tied, and 75-100% was "suboptimal overall" ([blog](https://tiiuae-tiny-h1-blogpost.hf.space/)). Conversely, the micro-LM paper pretrained 8.8-29.5M models on **100%** chat data (UltraChat, MOSS, Instruction_merge_set, 1.485B tokens) and got usable short dialogue openers ([arXiv 2604.19642](https://arxiv.org/abs/2604.19642)). The 10-20M knowledge-free, multi-turn-probe version is still untested. It should start from these two conflicting datapoints.
- **L8 (mask user-turn loss).** Loss on prompts vs masking has been studied: Instruction Modelling (Shi et al., NeurIPS 2024, 7B-13B; loss on instructions helps with long instructions, short outputs or little data) ([arXiv 2405.14394](https://arxiv.org/abs/2405.14394)); prompt-loss weight (Huerta-Enochian and Ko 2024; the PLW effect is significant, with 0.01-0.5 best for short completions) ([arXiv 2401.13586](https://arxiv.org/abs/2401.13586)); and SmolLM3's assistant-only loss (3B, cited in `lanes/posttrain.md`). What remains untested is the tiny-scale, pretraining-phase effect on role leaks and speaker binding.
- **L9 (upweight skill-bearing answer tokens).** Token reweighting toward tokens whose prediction depends on distant context is published: LongCE ([arXiv 2410.23771](https://arxiv.org/abs/2410.23771), re-weights "key tokens" in fine-tuning) and Token Weighting for Long-Range Language Modeling ([arXiv 2503.09202](https://arxiv.org/abs/2503.09202), NAACL 2025 Findings). Rho-1-style selective token loss is related but not re-checked here. L9 differs in knowing the answer spans from the skeleton rather than scoring them with a model, and in its scale (sizes in those papers not checked here; not tiny).
- **L10 (filter deflection from teacher outputs).** Phrase-based filtering of refusals and "AI language model" deflections from teacher data is established practice. ShareGPT_Vicuna_unfiltered (2023) removed conversations containing "text-based AI language model" and offered a variant without "I'm sorry, but" ([card](https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered)). Untested: the given-fact vs never-given-fact split, and its measured effect at tiny scale.
- **L11 (loss-masked assistant errors followed by corrections).** Physics of LMs Part 2.2 (GPT2-12-12, about 100M-class) pretrained on "erroneous solution steps immediately followed by their corrections". Accuracy rose; models did not learn to make more errors even at high error rates; and "it is not necessary to perform label masking on the errors". Fine-tuning a clean-pretrained model on retry data with LoRA, "label masking or not", did not significantly help ([arXiv 2408.16293](https://arxiv.org/abs/2408.16293)). That is math self-correction, not user corrections in chat. But it is in Planck's size range, and it argues for adding an **unmasked** arm to L11 and for putting such data into pretraining rather than a late stage.
- **L1 (partial).** Back-reference-dense training data has been put into small models in task-oriented dialogue. SimpleTOD fine-tuned GPT-2 on MultiWOZ dialogue-state tracking (cross-turn slot recall, scored programmatically by joint goal accuracy) ([arXiv 2005.00796](https://arxiv.org/abs/2005.00796)). The 5-20M, from-scratch, open-domain verified version remains untested as far as I could check. Related to L16: Parrot's controlled 20K comparison (13B) raised context-dependent queries per session (3.42 vs 1.45) and gained +0.24 MT-Bench, which amounts to a big-model density test.
- **No precedent found (limited search):** L4 (vocabulary knee with out-of-list eval), L13 (script-mode vs live-mode training comparison; TurnWise chose independently generated prior user turns to avoid drift and cost, but did not compare), L16 at tiny scale.

## 5. Omissions

1. **Micro language models (arXiv 2604.19642, Apr 2026).** 8.8-29.5M models (hidden 256-512, 8 or 16 layers, tied embeddings, GQA) pretrained from scratch **only on multi-turn chat data** (1.485B tokens) with a **12,288-token BPE**. The 14-29M models were "competitive with several 70M-256M-class baselines" on rubric-based short dialogue responses. In a 15-person study, a 28M opener plus Qwen3-235B-A22B continuation was rated equivalent to the standalone model 49% of the time. This is the nearest published point to Planck's headline size. It supports small-vocab tokenizers and high chat shares, but it tests response openers, not cross-turn memory.
2. **Brittleness result in Readability ≠ Learnability** (see claim 3). Planck should mix distributions and evaluate on out-of-template, real-user wording from the start, not only in L4.
3. **Skeleton-then-render precedents.** M2M "dialogue self-play" (2018) generated dialogue outlines with template utterances and semantic parses, then had crowd workers rewrite them, getting annotations for free ([arXiv 1801.04871](https://arxiv.org/abs/1801.04871)). The Schema-Guided Dialogue dataset (16k+ conversations, 16 domains; [arXiv 1909.05855](https://arxiv.org/abs/1909.05855)) came from the same line of work. SynthDST (2024) had an LLM render schema plus templates into dialogues with state labels ([arXiv 2402.02285](https://arxiv.org/abs/2402.02285)). The report cites only bAbI dialog. Its novelty items (a) and (c) should be restated as "applied to open-domain chat skills at a tiny-model register", not as a new pipeline.
4. **TII's 75% and 100% SFT-share arms** (see claim 9), which bear directly on L7.
5. **Physics of LMs 2.2** (see L11), the only in-range evidence on training with errors followed by corrections.
6. **User language models (arXiv 2510.06552, Oct 2025).** It reports that assistant LMs make poor user simulators and that "better assistants yield worse simulators". This bears on the live-mode simulator and on L14 (a second model rendering user turns). Script mode sidesteps it only if the teacher can still write realistic, imperfect user turns.
7. **`raincandy-u/TinyChat`** (100k rows, Apache-2.0). It is a license-clean small-talk baseline for L1's control arm (starhopp3r/TinyChat is CC-BY-NC-4.0), and it is the actual training set of TinyChat-1776K.
8. **Qwen3.5-9B's hybrid cache.** Only 8 of its 32 layers keep a KV cache (8 x 2 x 4 heads x 256 x 2 B = 32 KB per token). The 24 Gated DeltaNet layers carry a fixed per-sequence state of about 50 MB in fp32 (32 value heads x 128 x 128 x 4 B x 24 layers, derived; conv state excluded). A 1k-token render therefore costs about 80 MB vs about 336 MB for Gemma 4 12B (derived), which could fit about 4x more concurrent sequences on 24 GB. The report's KV comparison covers only Gemma. Whether MLX batches this architecture efficiently is unmeasured.
9. **Unverifiable Mac training throughput** (see claim 10c). The report carries the 10.6-11.8k tok/s figure without the fact-check's flag.
