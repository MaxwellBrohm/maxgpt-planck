What is NOT verified
  - No .ps1 file has executed anywhere (no PowerShell on the Mac). Written for Windows
    PowerShell 5.1, ASCII only. Most likely first-contact fixes: the PCIe ASPM powercfg
    alias, whether the Windows Update pause keys are honored on this build (the runbook
    says to look at Settings), and whether WSL starts from an S4U boot task (the runbook's
    reboot test; fallback -AtLogon).
  - setup_wsl.sh ran only through `bash -n`; its Linux parts (apt, cu128 torch, uv + vLLM)
    need the PC. runner_start.sh ran on the Mac through its tests.
  - No CUDA path has run: bench_micro and verify_cuda were exercised on CPU only. bf16,
    SDPA kernel choice, torch.compile and peak memory on the 5070 are unmeasured.
  - Whether WSL's nvidia-smi reports temperature: verify_cuda.py checks it; if not, set
    PLANCK_NVIDIA_SMI to the Windows nvidia-smi.exe (runner.env).
  - runner_start.sh's crash-restart loop (60 s sleep) is not tested (it would cost 60 s).

Design choices worth knowing
  - Runner, guard, heartbeat and add_job are stdlib only: they run under WSL's system
    python3; only the jobs use ~/planck/venv.
  - Job files: JSON in ~/planck/queue/pending, filename order. Experiments must name a
    committed prereg (checked with git on the PC); tools say no_prereg_reason instead.
  - Code reaches the PC as a git bundle (pc/mac/send_kit.sh), so the prereg check has real
    history and the PC holds no GitHub credential for the project repo. harness/ and pc/
    are untracked today: they must be committed (Max's call) before the bundle carries them.
    When committing, check that harness/runs/ (fake data, sample runs) is not swept in.
  - Separate venvs: ~/planck/venv (torch 2.13.0 cu128, same as the Mac) and
    ~/planck/venv-vllm (vLLM picks its own torch).
  - The status repo for heartbeats is not created; RUNBOOK step 10 is Max's (private repo
    + repo-scoped deploy key). heartbeat.py only pushes to an existing local clone, with git
    prompts disabled.
  - PLAN's "pull job configs from the status repo every 10 minutes" is NOT built: jobs are
    queued with add_job.py over SSH. A pull step belongs next to the heartbeat push later.
